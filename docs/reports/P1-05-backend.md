## 3. Technical decisions

- **Order of checks**: authenticate, active org from the session, membership re-checked in the org's transaction, `can()`, then input validation, then the handler. Input is parsed after authorization, so an unauthorized caller learns nothing about the input schema. Rejected: validating first.
- **Membership re-checked on every request.** The session's `activeOrgId` is only a pointer; a removed member or a tampered row gets `not_found` before anything else runs.
- **One transaction** for membership check, permission check, handler and success audit. Denials are audited and committed without running the handler. When a handler throws, its writes roll back and a separate `failure` (or `denied` for `forbidden`) event is written; programmer errors are then re-thrown, expected ones (`ActionError`, `OrgError`) become a result. This is why P1-04 needed `xInTx` forms: wrapping the old functions would have run check and change in two transactions.
- **Results, not exceptions**, for expected outcomes: `{ ok: false, code, message }` with C4 `ErrorCode` names. Messages carry no SQL, stack or internal path. Mapping to HTTP status stays in the API layer (engineering standards).
- **Type safety for permissions**: `permission` is a required property typed as the app's declared permission union. `action.types.test.ts` holds `@ts-expect-error` lines for a missing permission, an undeclared one, a role granting an undeclared permission, and a user action with an org permission; typecheck fails if any of them starts compiling. The same checks also run at startup for JavaScript callers.
- **`can()`**: an unknown role, an unknown permission, a non-string, prototype names (`__proto__`, `constructor`) and an error inside the policy all deny. Roles live in a `Map`, not an object, so prototype keys cannot match.
- **No escalation** in `defineOrgActions`: a caller may only invite to, assign, change or remove roles whose permissions they hold themselves (`isWithin`). An admin cannot invite an owner, promote themselves, or demote or remove the owner. Rejected: role-name rules ("admins cannot touch owners"), which `security.md` forbids as a replacement for permission checks.
- **The foundation grants no permission to `owner`.** Each app's role map decides. `owner` remains special only for the last-owner rule (P1-04).
- **User actions** (`defineUserAction`) for routes with no active org: `getMe`, `setActiveOrg`, create org, accept invitation. They use `session.read`/`session.update` (C4 v1.1 `ORG_INDEPENDENT_PERMISSIONS`), which every signed-in user has and no role map may declare. Their handlers get the database, not a transaction, because these operations span orgs; each P1-04 operation they call audits its change in its own transaction.
- **Strict input objects**: an `orgId`, `userId` or any unknown field in a request body is rejected (`validation_failed`), never read.
- **`requestId` must be a UUID** generated by the server; anything else throws.
- **`writeAudit` drops a `resourceId` that is not a UUID**, so a token or free text can never land in the audit log.

## 6. Remaining issues

- **Unauthenticated denials are audited but cannot be read back by the app role** (no actor and no org; RLS shows org-less rows only to their actor). They exist for an operator with database access.
- **User actions do not audit their own success**; they rely on the operation they call (all current ones do). A new user action must audit its change itself. Documented on `defineUserAction`.
- **No HTTP adapter yet.** Actions take `{ headers, input, requestId }` and return a result; mounting them as Next.js route handlers is P1-07, and as Engine routes P3-04.
- **The harness check that every route uses `defineAction`** is P2-05 (verification). Nothing here enforces it outside typecheck.
- **Hierarchical scopes** (org → team → project, explicit deny) are P7-01.
- Not run on Node 22 locally; CI runs Node 22.
